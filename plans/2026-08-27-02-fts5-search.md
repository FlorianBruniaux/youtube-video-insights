# SQLite FTS5 Search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and query a versioned local FTS5 index that returns safe, filtered, timestamped corpus results.

**Architecture:** `SQLiteFtsIndex` implements the domain `SearchIndex` port and owns schema/build/query details. `SearchService` owns user-query normalization, result grouping, and read-only use cases. Click remains a thin adapter.

**Tech Stack:** Python 3.11+, sqlite3/FTS5, Click, pytest

**Spec:** `plans/specs/SEARCH-ARCHITECTURE.md`

## Global Constraints

- Requires the domain models and corpus manifest from Plan 01.
- SQLite is a disposable derived index; source files remain the authority.
- A failed build must leave the prior database and manifest usable.
- The query path must not import or resolve an LLM backend.
- Never pass raw user text as an FTS expression.
- Store only corpus-relative paths.
- Add no third-party runtime dependency.

## Acceptance gate

- A complete VTT build publishes only after integrity validation.
- An interrupted or invalid build preserves the old index.
- One hundred hostile inputs execute without FTS or SQL errors.
- Filters have negative-boundary coverage.
- Default results contain no duplicate media IDs.
- Search opens the index read-only and performs no LLM or network call.
- Full-corpus build, memory, latency, and relevance gates are measured by Plan 03.
- The complete test suite passes.
